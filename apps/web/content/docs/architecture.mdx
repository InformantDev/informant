```text
GitHub branch/PR/comment ──webhook──▶ Tailscale Funnel lead
                                           │ tailnet dispatch
                              ┌────────────┴────────────┐
                              ▼                         ▼
                     Linux worker               macOS worker
                rootless Podman / host    Apple Container / Tart / host
                              └────────────┬────────────┘
                                           ▼
                                      GitHub Checks
```

When Tailscale is installed and Informant is configured as a lead, the lead publishes only the
signed GitHub webhook endpoint through Funnel. Each machine also exposes a small worker endpoint on
its Tailscale IPv4 address. The lead discovers online Informant peers from `tailscale status --json`
and dispatches repository notifications across the tailnet. Every notified machine performs one
GitHub synchronization and enters the existing capability-specific Checks election. Job definitions,
GitHub credentials, and secrets are never sent between workers.

A connected network worker does not run a timer or poll GitHub continuously. A lead performs one
synchronization at startup to recover events received while it was offline, then reacts to webhooks.
Startup recovery includes repositories advertised only by remote workers. Failed deliveries remain
queued with bounded exponential retries, and the lead refreshes peer topology so workers that join or
reconnect receive a recovery synchronization. Tag-push notifications bypass the normal tag throttle.
If Tailscale is not configured, `informant serve` retains the polling path. A configured worker never
silently falls back to polling when disconnected; reconnect Tailscale or explicitly run
`informant tailscale disable`. Funnel never exposes the private worker/build API.

Workers advertise `self-hosted`, their operating system, architecture, hostname, and optional custom
capabilities. A healthy selected container backend adds the dynamic `container` capability. Linux
probes rootless Podman directly; this is daemonless and does not depend on systemd. A worker filters jobs before entering the claim election, then groups them by normalized
`runs_on` requirements. Each requirement group is a separate claim scope. Workers with overlapping
capabilities therefore compete for shared jobs, while Linux and macOS workers can claim different jobs
for the same commit without stealing work from each other.

## Claim safety

The Checks API has no compare-and-swap operation. Informant resolves simultaneous claims by creating
an in-progress Check Run, re-reading all active claims, and electing the smallest GitHub check ID.
Only that claimant starts a VM; the others complete themselves as cancelled. This removes duplicate
execution after the race is visible to GitHub while keeping GitHub as the only shared coordination
system.

The elected `Informant CI` check remains the build-level claim and summary. Informant creates a
separate `Informant / <job>` check for every selected job. Each job check moves from queued to running
to its own conclusion and contains only that job's log, so parallel output is never interleaved in the
GitHub UI. While a job runs, Informant updates its check with a rolling log tail about every 10 seconds.
Updates are coalesced to avoid an API request per output chunk. The CLI exposes the retained local log,
which is capped at 10 MiB per build and includes a truncation marker when output exceeds that limit.
Jobs skipped because a dependency failed receive a `skipped` conclusion.

Because the Checks API does not offer compare-and-swap, this election is best-effort rather than a
strict distributed lock. Checks are fetched with `filter=all` and scoped to the configured GitHub App;
claims left behind by dead workers become retryable after 24 hours.

Claims are scoped to event identity, so a commit and each newly-created PR conversation comment on
the same SHA elect independently. Comment runs use the distinct `Informant CI / comment` check name.

Manual runs add a queued check. The next claimant consumes that request and runs even if the commit
already has an older completed result.

Automatic builds are grouped into branch and pull-request lanes. When synchronization observes a new SHA in a
lane, the worker that owns the previous SHA aborts its commands, cleans up its Tart VMs, and concludes
its checks as cancelled. Every notified machine checks the same registered repository heads, so this cancellation
does not depend on the machine that claims the replacement build. Manual and comment-triggered runs are
not part of an automatic lane and are never superseded by a push.

GitHub UI re-runs use the same path. Clicking **Re-run** resets Informant's Check Suite to queued.
Workers observe that state after a `check_suite` webhook or during the next polling cycle, elect one
claimant, and create a fresh Check Run.
