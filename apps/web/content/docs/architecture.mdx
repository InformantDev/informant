title: Architecture
description: How GitHub Checks act as a decentralized work queue.
---

```text
GitHub branch/PR/comment ──poll──▶ Linux worker ──▶ native checkout
                                  macOS worker ──▶ Apple Container / Tart VM
                                        │
                                        ▼
                                  GitHub Checks
```

Workers advertise `self-hosted`, their operating system, architecture, hostname, and optional custom
capabilities. A worker filters jobs before entering the claim election, and the eligible job set is
part of the claim scope. Linux and macOS workers can therefore claim different jobs for the same
commit without stealing work from each other.

## Claim safety

The Checks API has no compare-and-swap operation. Informant resolves simultaneous claims by creating
an in-progress Check Run, re-reading all active claims, and electing the smallest GitHub check ID.
Only that claimant starts a VM; the others complete themselves as cancelled. This removes duplicate
execution after the race is visible to GitHub while keeping GitHub as the only shared coordination
system.

The elected `Informant CI` check remains the build-level claim and summary. Informant creates a
separate `Informant / <job>` check for every selected job. Each job check moves from queued to running
to its own conclusion and contains only that job's log, so parallel output is never interleaved in the
GitHub UI. While a job runs, Informant updates its check with a rolling log tail about every 10 seconds.
Updates are coalesced to avoid an API request per output chunk. The CLI exposes the retained local log,
which is capped at 10 MiB per build and includes a truncation marker when output exceeds that limit.
Jobs skipped because a dependency failed receive a `skipped` conclusion.

Because the Checks API does not offer compare-and-swap, this election is best-effort rather than a
strict distributed lock. Checks are fetched with `filter=all` and scoped to the configured GitHub App;
claims left behind by dead workers become retryable after 24 hours.

Claims are scoped to event identity, so a commit and each newly-created PR conversation comment on
the same SHA elect independently. Comment runs use the distinct `Informant CI / comment` check name.

Manual runs add a queued check. The next claimant consumes that request and runs even if the commit
already has an older completed result.

Automatic builds are grouped into branch and pull-request lanes. When polling observes a new SHA in a
lane, the worker that owns the previous SHA aborts its commands, cleans up its Tart VMs, and concludes
its checks as cancelled. Every machine polls the same registered repository heads, so this cancellation
does not depend on the machine that claims the replacement build. Manual and comment-triggered runs are
not part of an automatic lane and are never superseded by a push.

GitHub UI re-runs use the same path. Clicking **Re-run** resets Informant's Check Suite to queued.
Workers observe that state through the Checks API, elect one claimant, and create a fresh Check Run.
Informant does not need a public webhook endpoint to receive the re-run request.
