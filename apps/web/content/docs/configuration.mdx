title: TOML configuration
description: GitHub Actions-like jobs without YAML.
---

Informant reads shared defaults from `.informant/config.toml` and loads every `.toml` file in
`.informant/jobs/` from the commit it is about to run. One job per file keeps larger pipelines easy to
navigate and review.

`.informant/config.toml`:

```toml
version = 1
timeout_minutes = 60
triggers = [
  { event = "commit" },
  { event = "comment", pull_request = { state = "open", draft = false, base_branches = ["main"] } }
]
filters = []

[container]
image = "docker.io/oven/bun:1"
cpu = 2
memory_mb = 2048
prepare = "apt-get update && apt-get install -y git"
```

Informant polls every 30 seconds by default. Set `poll_interval_seconds` only when a repository needs
a different cadence; values below five seconds are clamped to five.

The top-level `container` or `vm` table is the default runtime for every job. Existing configurations
with `[vm]` remain valid. A job can override the default with an inline `container` or `vm` table; the
two are mutually exclusive. An override of the same runtime type inherits omitted fields, so jobs can
provide their own preparation without repeating the image. For example:

```toml
[[jobs]]
name = "linux-e2e"
command = "bun run test:e2e"
runs_on = ["linux", "x64"]
host = {}

[[jobs]]
name = "macos-e2e"
command = "bun run test:e2e"
runs_on = ["darwin", "arm64"]
vm = { image = "ghcr.io/cirruslabs/macos-tahoe-base:latest", os = "macos", user = "admin", password = "admin", cpu = 4, memory_mb = 8192, prepare = "brew install playwright" }
```

`runs_on` uses GitHub Actions-style AND matching: the worker must provide every listed capability.
Every worker automatically provides `self-hosted`, its platform (`linux` or `darwin`), architecture
(`x64` or `arm64`), and lowercase hostname. Add custom comma-separated labels with
`INFORMANT_CAPABILITIES`, for example `INFORMANT_CAPABILITIES=gpu,large`.

Allowed host mounts advertise protected `mount:<name>` capabilities automatically. These labels
cannot be added through `INFORMANT_CAPABILITIES`; they exist only while the mount is in the worker's
machine-local allowlist **and** its source currently resolves to a regular file no larger than 1 MiB.
An unusable allowlist source is omitted from the worker's capabilities and emits a
`Not advertising mount:<name>` diagnostic with the reason.

Workers also provide `container` only when their platform backend passes its health check. Use
`runs_on = ["container"]` for a portable container job that can run with Apple Container on macOS or
rootless Podman on Linux. Generated jobs use this label. Version 1 configurations that omit `runs_on`
for non-host jobs retain the legacy `["darwin", "arm64"]` behavior.

`host = {}` runs the command directly on the worker in a fresh detached checkout with an isolated
home directory. It is intentionally explicit because repository code is not isolated from the host;
use it only for trusted repositories. Persistent Informant caches are not supported for host jobs,
and `runs_on` is required. Existing container and VM jobs without `runs_on` default to
`["darwin", "arm64"]`, preserving their Apple Silicon worker behavior while preventing Linux workers
from claiming them.

Jobs with the same normalized `runs_on` labels share one claim election. Workers with additional
capabilities still compete for shared jobs instead of executing them twice. A job and every job in its
`needs` chain must use the same `runs_on` labels; cross-worker dependency chains are rejected.

Container jobs use [Apple Container](https://github.com/apple/container) on Apple Silicon macOS and
rootless [Podman](https://podman.io/) on Linux. Podman runs directly as the worker user without a
daemon, socket, systemd unit, or rootful service. Informant rejects rootful Podman and does not
advertise the `container` capability when the selected backend is missing or unhealthy. Run
`informant setup` to install and verify it.

Jobs run as UID 0 inside the container with the checkout mounted at `/workspace`. With rootless
Podman, container root maps into the unprivileged worker user's namespace; Informant also adds
`--security-opt no-new-privileges`. On SELinux hosts, Podman privately relabels the disposable job
workspace with `:Z` and uses shared `:z` labels for Informant cache mounts. This preserves SELinux
separation between job workspaces while allowing intentionally shared caches to be mounted by multiple
containers. Apple Container uses its own lightweight VM isolation. CPU and memory limits apply on both
backends. Rootless Podman also requires cgroups v2 so those limits are enforceable. Cache directories
use isolated host storage under `/home/root`.
Declared secrets are inherited by name from the client environment, never included in command
arguments, and redacted using the same policy as VMs. Prefer fully qualified image references such as
`docker.io/oven/bun:1` so registry resolution is consistent across backends.

Informant mounts the checkout and other Tart shared directories beneath `/mnt/shared` on Linux;
Linux user caches are beneath `/home/<user>`. On macOS, these remain `/Volumes/My Shared Files` and
`/Users/<user>` respectively. The Linux image must allow the configured user to mount Tart's
VirtioFS share with passwordless `sudo`.

`.informant/jobs/test.toml`:

```toml
name = "test"
runs_on = ["container"]
command = """
set -euo pipefail
bun install --frozen-lockfile
bun test
"""
environment = { CI = "true" }
secrets = ["DEPLOY_TOKEN"]
cache = [{ paths = ["~/.bun/install/cache"], shared = true }]
```

`.informant/jobs/lint.toml`:

```toml
name = "lint"
runs_on = ["container"]
command = """
bun run check
"""
timeout_minutes = 10
optional = true
triggers = [
  { event = "commit", pull_request = { state = "open", draft = false } },
  { event = "comment", pull_request = { state = "open" } }
]
```

`.informant/jobs/build.toml`:

```toml
name = "build"
runs_on = ["container"]
command = """
bun run build
"""
timeout_minutes = 20
needs = ["test", "lint"]
triggers = [{ event = "commit" }]
filters = [{ branch = { names = ["main"] } }]
```

Top-level `timeout_minutes` is inherited by every job. Set `timeout_minutes` on an individual job only
when it needs a different limit.

Jobs are required by default. Set `optional = true` on a non-blocking job: Informant still records
and displays a failure, but reports its GitHub check as neutral, keeps the aggregate build successful,
and allows jobs that depend on it to run. Setup and reporting errors outside the job itself still fail
the build.

Like GitHub Actions, jobs run in parallel by default. Each job gets an isolated checkout in its
configured container, native host runtime, or Tart VM. Use `needs` to make a job wait for one or more
other jobs. Linux guests instead use `/mnt/shared/workspace`. In this example, `test` and `lint` start
together; `build` starts only after both pass.
If a dependency fails or times out, jobs that need it are skipped.

## Host secrets

Jobs receive no host secrets by default. Declare the environment variable names a job needs with
`secrets`; Informant fails the job before starting its VM when a requested value is unavailable:

```toml
secrets = ["AMP_API_KEY", "DEPLOY_TOKEN"]
```

Set each value on the worker with an `INFORMANT_SECRET_` prefix. Informant removes that prefix in the
VM, so `INFORMANT_SECRET_AMP_API_KEY` becomes `AMP_API_KEY` for the job:

```bash
export INFORMANT_SECRET_AMP_API_KEY="sgamp_..."
informant startup enable
```

`startup enable` captures `INFORMANT_*` values in the mode-`600` LaunchAgent or systemd user-service
definition; rerun it
after changing a secret. The prefix is required for foreground workers too, preventing a repository
from requesting unrelated variables in the host environment. Secret names must be shell variable
names and cannot also appear in `environment`. Values are written to a mode-`600` temporary file,
mounted only into that job's VM, sourced without appearing in the SSH command line, and deleted with
the build workspace. Informant masks exact secret values in streamed and stored logs as defense in
depth, but jobs must still not print, encode, or otherwise expose their secrets.

`GITHUB_TOKEN` is special: when requested, Informant supplies its short-lived GitHub App installation
token automatically. Informant mints it when the job starts, limits it to the current repository, and
grants only pull-request write access. Static GitHub tokens cannot be forwarded this way.

Secret-bearing jobs are trust-sensitive. For commits not yet on the default branch, Informant ignores
that commit's version of every secret-bearing job and uses the job definition, VM configuration, and
authorization from the current default-branch commit. A pull request therefore cannot add a secret,
change the trusted command, select a hostile VM image, or remove a required secret-bearing job. The
trusted command may inspect the proposed checkout, but it must not execute scripts or install packages
from that checkout while secrets are present.

## Allowed host file mounts

Container jobs can request host files by a machine-local allowlist name. The repository never
specifies a host path. Mount names use lowercase letters, numbers, dots, underscores, and dashes.
First allow an existing file on the worker:

```bash
informant mount allow codex-auth "$HOME/.codex/auth.json"
```

If a Codex login is stored only in the system keychain, create the file-backed login first with
`codex -c 'cli_auth_credentials_store="file"' login`.

Then request that name from a job and choose a container directory. Informant mounts a temporary
directory containing the file under its original basename:

```toml
environment = { CODEX_HOME = "/mnt/informant-codex" }
mounts = [{ source = "codex-auth", target = "/mnt/informant-codex", write_back = true }]
runs_on = ["container", "mount:codex-auth"]
```

Using the corresponding `mount:codex-auth` capability prevents workers without that allowlist entry
from claiming the job.

`write_back` defaults to `false`. When enabled, Informant serializes jobs using the same writable
source and atomically copies the resulting file back to the allowed host path unless the host copy
changed during the job. This supports files such as Codex's `auth.json`, whose tokens may refresh
during a run, without overwriting a newer host-side refresh. Mounted files are limited to 1 MiB.
Informant redacts the original and refreshed file contents and JSON string values from job logs,
exposes no other files from the source directory, and applies the same default-branch trust
protections as secret-bearing jobs. Because a writable credential may rotate to a value that was
already printed, jobs with `write_back = true` suppress all child stdout and stderr and emit a
suppression marker instead. Read-only mounts retain non-secret output after delayed redaction.

Use `informant mount list` to inspect the allowlist and `informant mount remove <name>` to revoke an
entry. Treat mounted credentials like other automation secrets: use them only on trusted private
workers and restrict who can add branches to repositories that request them.

## Automatic triggers

Events are `commit` and `comment`. A commit rule can filter either exact branch names or pull requests.
A comment rule can only use the optional pull-request filter and means a newly created PR conversation
comment—not an edit or line-level review comment. With no branch or pull-request table, a commit
matches branches and active same-repository PR heads.

Tag builds are opt-in commit triggers. Put one or more glob patterns in a `tag` table:

```toml
triggers = [{ event = "commit", tag = { patterns = ["v*", "release/*"] } }]
```

A trigger may use only one context table: `branch`, `tag`, or `pull_request`. `tag` is valid only
with `event = "commit"`. Patterns match the entire tag name, are case-sensitive, and let `*` and `?`
match across `/`; for example, `release/*` matches `release/v2` but not `Release/v2`. Untagged commit
rules do not run for tags.

Pull-request `state` is `open`, `closed`, or `all`; `draft` and exact `base_branches` are optional.
Closed PRs are resolved when a new conversation comment arrives, so `state = "closed"` is useful for
comment triggers. Commit polling considers active PR heads rather than replaying every historical
closed PR. Fork PR heads are not executed.

Jobs inherit top-level triggers. A job's own `triggers` replaces them; `triggers = []` makes it manual-
or dependency-only. Matching rules are ORed, and dependencies of matching root jobs are always added.
Legacy `branches` still becomes commit branch rules (default `main`), but cannot be combined with
top-level `triggers`. Manual runs ignore trigger eligibility, except that branch constraints embedded
in existing trigger rules remain enforced for compatibility. Prefer job filters for new configuration.

Top-level `filters` are inherited by jobs. A job's own `filters` replaces them, and `filters = []`
opts out. Filters constrain root-job eligibility independently of triggers. Use branch filters for jobs
that must only run on exact branch names, including when manually requested:

```toml
triggers = [{ event = "commit" }]
filters = [{ branch = { names = ["main", "release"] } }]
```

Every filter must match; names within a branch filter are ORed and matched exactly. A branch filter
requires a real branch context, so tags, pull-request commits, and pull-request comments do not match
one. Filters apply to automatic runs and GitHub manual triggers. Local `informant run --local`
executions bypass filters and do not create GitHub checks. Dependencies of selected roots are still
added even when their own filters do not match, just as their triggers are not independently
evaluated.

## Prepared runtime images

`vm.prepare` and `container.prepare` run once when a worker first sees that image and preparation
command. Informant keeps the result as a local Tart or OCI image and starts jobs from it, so tools do
not need to be installed in every job. Container preparation builds an isolated OCI image with the
selected backend. It does not receive the job checkout, environment, caches, or
secrets by default. Changing the source image or preparation command creates a new prepared image.
Because preparation is part of the runtime table, different jobs can use different preparation
commands.

Podman preparation uses `--force-rm` to remove intermediate Buildah containers after failures. Cleanup
is best effort: abrupt process termination can still leave internal Buildah state for Podman's own
cleanup tooling. Informant does not run a global Podman prune because that could delete non-Informant
build or image state owned by the same user.

Informant tracks which configured repository jobs use each prepared Tart or container image.
When the final reference moves to another image, or a repository or job is removed, idle housekeeping
deletes the unreferenced image. `informant image prune` runs that cleanup immediately.

Container runtimes can declare repository-relative files or glob patterns with `prepareInputs`.
Informant copies matching files into the image's `/workspace`, exposes that path as
`$INFORMANT_PREPARE_ROOT` during preparation, and includes their paths, modes, and contents in the
image identity. Every pattern must match at least one regular file; absolute paths, parent traversal,
and symbolic links are rejected. Preparation output such as `node_modules` remains in the image as an
immutable layer. At runtime, Informant copies the job checkout into this container-local workspace
without removing prepared files, then runs the job there. A lockfile change prepares a new image;
ordinary source changes reuse the installed dependencies:

```toml
container.image = "docker.io/oven/bun:1"
container.prepareInputs = ["bun.lock", "package.json", "apps/*/package.json"]
cache = []
container.prepare = """
cd "$INFORMANT_PREPARE_ROOT"
bun install --frozen-lockfile --ignore-scripts
"""
```

The corresponding job command should use the baked dependencies directly rather than running
`bun install` again.

Preparation is automatic. `informant image prepare` warms configured Tart VM images, while the first
container job warms its prepared container image. `informant image list` lists prepared Tart
images, and `informant image prune` removes unreferenced prepared images from both runtimes. Use
`container image` on macOS or `podman image` on Linux to inspect the full inventory. Every worker prepares its own local
copy, which keeps multi-machine setup automatic.

## Persistent job caches

`environment` and `cache` can be declared in `.informant/config.toml` as defaults inherited by every
job. A job's environment values override matching defaults; a job-level `cache` replaces the default
cache list. This keeps repository-wide package and build caches in one place:

```toml
environment = { TURBO_CACHE_DIR = "/Users/admin/.cache/turborepo", TURBO_CACHE_MAX_AGE = "14d", TURBO_CACHE_MAX_SIZE = "10GB" }
cache = [
  { paths = ["~/.bun/install/cache"], shared = true },
  { paths = ["~/.cache/turborepo"], shared = true },
]
```

`jobs.cache` is an array of cache groups. Set `shared = true` for a concurrency-safe,
content-addressed package cache such as `~/.bun/install/cache`. Jobs in the same build mount one
Informant-owned host directory directly. A default-branch build uses the persistent machine-wide
cache; pull requests and other commits receive a build-scoped cache that is deleted afterward, so
untrusted code cannot poison a later trusted build. Set `build_scoped = true` alongside
`shared = true` to force this per-build isolation for trusted builds too, such as when handing
ordinary per-build caches. For a credential-free producer-to-publisher artifact channel, also set
`protected_channel = true`; jobs requesting that dedicated channel are pinned to the trusted
configuration. A container-job consumer can additionally set `read_only = true`, and receives the
channel mount read-only. Shared caches cannot use `key_files`. The
host's personal cache is never exposed to CI code.

Without `shared`, each group associates one or more guest `paths` with its `key_files`. Informant
restores those paths from persistent host storage before the job and saves them afterward, isolated
by repository, job, and key-file contents in compressed archives. Missing key files do not fail the job. Use
`informant cache path` to locate the cache root. Informant retains the current and most recent keyed
version, removing older versions after seven days. The worker applies that policy globally while idle,
removes cache trees for repositories no longer assigned to it, and enforces its configured keyed-cache
quota. `informant cache prune` removes keyed caches while preserving shared caches; `informant cache
clear` removes everything. Shared caches are only removed automatically as a last resort when the host
is below its configured free-space target.

Prepared images and caches serve different purposes: put runtimes and system packages in
`vm.prepare`; use `jobs.cache` for downloaded dependencies and compiler caches. Checkouts and all
uncached VM changes remain disposable.
