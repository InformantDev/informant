---
title: TOML configuration
description: GitHub Actions-like jobs without YAML.
---

Informant reads shared defaults from `.informant/config.toml` and loads every `.toml` file in
`.informant/jobs/` from the commit it is about to run. One job per file keeps larger pipelines easy to
navigate and review.

`.informant/config.toml`:

```toml
version = 1
timeout_minutes = 60
triggers = [
  { event = "commit", branch = { names = ["main", "release"] } },
  { event = "comment", pull_request = { state = "open", draft = false, base_branches = ["main"] } }
]

[container]
image = "oven/bun:1"
cpu = 2
memory_mb = 2048
prepare = "apt-get update && apt-get install -y git"
```

Informant polls every 30 seconds by default. Set `poll_interval_seconds` only when a repository needs
a different cadence; values below five seconds are clamped to five.

The top-level `container` or `vm` table is the default runtime for every job. Existing configurations
with `[vm]` remain valid. A job can override the default with an inline `container` or `vm` table; the
two are mutually exclusive. An override of the same runtime type inherits omitted fields, so jobs can
provide their own preparation without repeating the image. For example:

```toml
[[jobs]]
name = "linux-e2e"
command = "bun run test:e2e"
container = { prepare = "apt-get update && apt-get install -y chromium" }

[[jobs]]
name = "macos-e2e"
command = "bun run test:e2e"
vm = { image = "ghcr.io/cirruslabs/macos-tahoe-base:latest", os = "macos", user = "admin", password = "admin", cpu = 4, memory_mb = 8192, prepare = "brew install playwright" }
```

Container jobs require [Apple Container](https://github.com/apple/container) and run as UID 0 with the
checkout mounted at `/workspace`. Cache directories use isolated host storage under `/home/root` in
the container. Declared secrets are inherited by name from the Container client environment, never
included in command arguments, and redacted using the same policy as VMs.

Informant mounts the checkout and other Tart shared directories beneath `/mnt/shared` on Linux;
Linux user caches are beneath `/home/<user>`. On macOS, these remain `/Volumes/My Shared Files` and
`/Users/<user>` respectively. The Linux image must allow the configured user to mount Tart's
VirtioFS share with passwordless `sudo`.

`.informant/jobs/test.toml`:

```toml
name = "test"
command = """
set -euo pipefail
bun install --frozen-lockfile
bun test
"""
environment = { CI = "true" }
secrets = ["DEPLOY_TOKEN"]
cache = [{ paths = ["~/.bun/install/cache"], shared = true }]
```

`.informant/jobs/lint.toml`:

```toml
name = "lint"
command = """
bun run check
"""
timeout_minutes = 10
triggers = [
  { event = "commit", pull_request = { state = "open", draft = false } },
  { event = "comment", pull_request = { state = "open" } }
]
```

`.informant/jobs/build.toml`:

```toml
name = "build"
command = """
bun run build
"""
timeout_minutes = 20
needs = ["test", "lint"]
```

Top-level `timeout_minutes` is inherited by every job. Set `timeout_minutes` on an individual job only
when it needs a different limit.

Like GitHub Actions, jobs run in parallel by default. Each job gets its own fresh container or Tart VM
and isolated checkout. Use `needs` to make a job wait for one or
more other jobs. Linux guests instead use `/mnt/shared/workspace`. In this example, `test` and `lint`
start together; `build` starts only after both pass.
If a dependency fails or times out, jobs that need it are skipped.

## Host secrets

Jobs receive no host secrets by default. Declare the environment variable names a job needs with
`secrets`; Informant fails the job before starting its VM when a requested value is unavailable:

```toml
secrets = ["AMP_API_KEY", "DEPLOY_TOKEN"]
```

Set each value on the worker with an `INFORMANT_SECRET_` prefix. Informant removes that prefix in the
VM, so `INFORMANT_SECRET_AMP_API_KEY` becomes `AMP_API_KEY` for the job:

```bash
export INFORMANT_SECRET_AMP_API_KEY="sgamp_..."
informant startup enable
```

`startup enable` captures `INFORMANT_*` values in the mode-`600` LaunchAgent definition; rerun it
after changing a secret. The prefix is required for foreground workers too, preventing a repository
from requesting unrelated variables in the host environment. Secret names must be shell variable
names and cannot also appear in `environment`. Values are written to a mode-`600` temporary file,
mounted only into that job's VM, sourced without appearing in the SSH command line, and deleted with
the build workspace. Informant masks exact secret values in streamed and stored logs as defense in
depth, but jobs must still not print, encode, or otherwise expose their secrets.

`GITHUB_TOKEN` is special: when requested, Informant supplies its short-lived GitHub App installation
token automatically. Informant mints it when the job starts, limits it to the current repository, and
grants only pull-request write access. Static GitHub tokens cannot be forwarded this way.

Secret-bearing jobs are trust-sensitive. For commits not yet on the default branch, Informant ignores
that commit's version of every secret-bearing job and uses the job definition, VM configuration, and
authorization from the current default-branch commit. A pull request therefore cannot add a secret,
change the trusted command, select a hostile VM image, or remove a required secret-bearing job. The
trusted command may inspect the proposed checkout, but it must not execute scripts or install packages
from that checkout while secrets are present.

## Automatic triggers

Events are `commit` and `comment`. A commit rule can filter either exact branch names or pull requests.
A comment rule can only use the optional pull-request filter and means a newly created PR conversation
comment—not an edit or line-level review comment. With no branch or pull-request table, a commit
matches branches and active same-repository PR heads.

Pull-request `state` is `open`, `closed`, or `all`; `draft` and exact `base_branches` are optional.
Closed PRs are resolved when a new conversation comment arrives, so `state = "closed"` is useful for
comment triggers. Commit polling considers active PR heads rather than replaying every historical
closed PR. Fork PR heads are not executed.

Jobs inherit top-level triggers. A job's own `triggers` replaces them; `triggers = []` makes it manual-
or dependency-only. Matching rules are ORed, and dependencies of matching root jobs are always added.
Legacy `branches` still becomes commit branch rules (default `main`), but cannot be combined with
top-level `triggers`. Manual `informant run` ignores trigger eligibility.

## Prepared runtime images

`vm.prepare` and `container.prepare` run once when a worker first sees that image and preparation
command. Informant keeps the result as a local Tart or OCI image and starts jobs from it, so tools do
not need to be installed in every job. Container preparation builds an isolated image with Apple
Container's BuildKit integration. It does not receive the job checkout, environment, caches, or
secrets by default. Changing the source image or preparation command creates a new prepared image.
Because preparation is part of the runtime table, different jobs can use different preparation
commands.

Container runtimes can declare repository-relative files or glob patterns with `prepareInputs`.
Informant copies matching files into `$INFORMANT_PREPARE_ROOT` while preparing the image and includes
their paths, modes, and contents in the image identity. Every pattern must match at least one regular
file; absolute paths, parent traversal, and symbolic links are rejected. The inputs are removed from
the resulting filesystem after preparation. This can seed an immutable package cache without sharing
a writable cache between concurrent jobs:

```toml
container.image = "oven/bun:1"
container.prepareInputs = ["bun.lock", "package.json", "apps/*/package.json"]
cache = []
container.prepare = """
cd "$INFORMANT_PREPARE_ROOT"
bun install --frozen-lockfile --ignore-scripts
"""
```

Preparation is automatic. `informant image prepare`, `informant image list`, and `informant image
prune` currently manage prepared Tart VM images. Container preparation is warmed automatically by the
first job that uses it; inspect or remove those images with `container image`. Every worker prepares
its own local copy, which keeps multi-machine setup automatic.

## Persistent job caches

`environment` and `cache` can be declared in `.informant/config.toml` as defaults inherited by every
job. A job's environment values override matching defaults; a job-level `cache` replaces the default
cache list. This keeps repository-wide package and build caches in one place:

```toml
environment = { TURBO_CACHE_DIR = "/Users/admin/.cache/turborepo", TURBO_CACHE_MAX_AGE = "14d", TURBO_CACHE_MAX_SIZE = "10GB" }
cache = [
  { paths = ["~/.bun/install/cache"], shared = true },
  { paths = ["~/.cache/turborepo"], shared = true },
]
```

`jobs.cache` is an array of cache groups. Set `shared = true` for a concurrency-safe,
content-addressed package cache such as `~/.bun/install/cache`. Jobs in the same build mount one
Informant-owned host directory directly. A default-branch build uses the persistent machine-wide
cache; pull requests and other commits receive a build-scoped cache that is deleted afterward, so
untrusted code cannot poison a later trusted build. Shared caches cannot use `key_files`. The host's
personal cache is never exposed to CI code.

Without `shared`, each group associates one or more guest `paths` with its `key_files`. Informant
restores those paths from persistent host storage before the job and saves them afterward, isolated
by repository, job, and key-file contents in compressed archives. Missing key files do not fail the job. Use
`informant cache path` to locate the cache root. Informant retains the current and most recent keyed
version, removing older versions after seven days. `informant cache prune` removes keyed caches while
preserving shared caches; `informant cache clear` removes everything.

Prepared images and caches serve different purposes: put runtimes and system packages in
`vm.prepare`; use `jobs.cache` for downloaded dependencies and compiler caches. Checkouts and all
uncached VM changes remain disposable.
